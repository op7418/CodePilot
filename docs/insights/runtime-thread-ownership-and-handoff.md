# 为什么聊天不再原地切 Runtime

> 技术实现见 [docs/handover/runtime-thread-ownership-and-handoff.md](../handover/runtime-thread-ownership-and-handoff.md)

## 表面自由与真实结果不是一回事

原来的交互很自由：聊天中随时点 Claude Code、CodePilot 或 Codex。但用户以为自己只是“换个引擎继续聊”，底层发生的事并不一致。

- Claude Code 会把数据库历史重新包装后交给一个 SDK session。
- CodePilot 每轮从数据库重放消息。
- Codex 主要续自己的 thread；第一次中途切入时并不会天然拥有另两条 Runtime 的完整记忆。

因此，同一个聊天气泡序列不等于同一个底层上下文。最坏的情况不是一次报错，而是它看起来继续成功了，实际漏掉前文；再切回来又恢复另一条旧分支。用户很难知道回答建立在哪份历史上。

## 为什么收益不成比例

原地跨 Runtime 的真实使用频率低，却让所有日常路径承担成本：

- 每次发送都要考虑当前 pin、全局默认、Provider、模型和两个原生 session ref 谁优先；
- 后台 welcome、heartbeat、重试、Bridge 可能在用户没选择时替会话占用另一 Runtime；
- 一次切换通常会改变底层 session 和 prompt 前缀，缓存从头建立；
- 测试必须覆盖来回切换后的多条隐形历史分支。

这些复杂度不只服务于主动切换者，还会影响从不切换的绝大多数聊天。用户自己很少使用这项能力，是一个很强的产品信号：不该让罕见操作决定主路径架构。

## 新取舍：稳定聊天，先锁 Runtime

第一次执行后，聊天固定一个 Runtime owner，Composer 左侧的 Runtime 选择直接置灰。模型选择器仍可使用，但只展示当前 Runtime 内能兑现的变化。

跨 Runtime 的技术交接能力仍然保留，但普通下拉框不再触发它。实机测试证明，“看起来只是切换选项，实际突然创建并跳到新聊天”同样是不透明的交互。未来如果重新开放，必须是独立写明“在新聊天中继续”的动作，并在执行前解释这些结果：

- 原聊天完整保留，可随时返回；
- 新聊天清楚显示来源、覆盖到哪条消息、是否截断；
- 三种 Runtime 收到同一份交接事实；
- 界面明确说明原生 thread 和缓存没有迁移。

这比“透明迁移”少一点魔法，多一点可解释性。对于编程任务，可解释性更重要：用户应该知道自己是在新建交接分支，而不是点完普通选项后才发现页面被切走。

## 同 Runtime 为什么仍允许变化

Runtime owner 不等于模型永远锁死。同一 Runtime 内，有些变化可以安全完成：Codex thread 可原地换模型；Claude/Native 可以重放规范化数据库历史后建立新底层上下文。

关键不是“一律禁止”，而是让 Runtime 自己声明四种结果：原地继续、重放上下文、新聊天、完全不支持。前端只展示服务端能兑现的动作，不再按模型名称或 Provider 品牌猜。

## 对缓存和成本的预期

可以确定的收益：

- 无意跨 Runtime 导致的缓存重建被消除；
- 同一聊天不会因全局默认变化而漂移；
- 跨 Runtime 丢前文/回旧分支这类结构性错误被合同阻止。

不能提前承诺的收益：具体节省多少 token 或费用。不同 Provider 对 cache read/write 的报告不同，旧数据还把未知费用合并成过 0。实现先修正事实口径：缺 bucket 就显示未知，SDK 合成的 0 不当作 Provider 事实，stable owner 与 handoff 分 cohort。只有真实样本积累后，才适合回答“平均省了多少”。

## 压缩为什么也要按 Runtime 说实话

长聊天压缩与换 Runtime 都会影响底层上下文和缓存。Claude/Native 可以由 CodePilot 主动生成摘要；Codex 的 thread 压缩由 Runtime 管理。统一显示“压缩发生了”不等于统一声称“CodePilot 控制了全部压缩”。

所以产品展示的是可证明的事实：覆盖边界、使用的辅助模型、估算节省、是否重建底层 session。估算只用于容量提示，不进入账单。

## 代价与剩余问题

- 当前聊天不能从普通 Composer 直接跨 Runtime；用户需要主动新建聊天。未来若提供显式交接入口，会多一个新聊天，侧栏数量可能增加。
- 交接首版使用有明确截断提示的最近 transcript window，不承诺完整语义摘要。
- 同 Runtime capability 仍需随协议变化维护，特别是 Codex thread 行为。
- 真正的缓存收益需要真实 Provider 样本，单测无法代替。

这些代价是可见、可测、可继续改进的；原地切换的问题则常常是静默的。新设计优先消除静默错误，再逐步优化交接体验。
